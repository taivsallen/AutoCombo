# Web 轉珠求解器：更新幅度的驗收方法

本次目標是 160ms 預算內交付已找到的最佳候選。合法路徑、需求達成、最大 combo、最短步數是不同問題；任何一項改善都不能代替其他項目的證據。

## 版本與計時邊界

- 前版：本次修改前保存的 `baseline/App.jsx`，SHA256 `d6dca95535a958186b459450cf2f15d9c9885102cae12e90a870f39c3ef301df`。這是此次工作開始時的 Web 程式，沒有推稱它等於某個已發布版本。
- 新版：每份實驗 JSON 保存實際讀入的檔案 hash、設定、seed、時間與工具 hash；實驗期間若程式改動，該次結果不得沿用。
- 主驗收使用 production build。開發模式、首次執行、暖機後、快取命中、未命中分別記錄。
- 同一台裝置、瀏覽器版本、電源模式、可見前景頁面執行；不要一邊跑 A/B 一邊跑其他壓力測試。此次裝置為 i5-9300H，4 核心／8 邏輯處理器，Node v24.11.1；瀏覽器結果使用 Codex 內建瀏覽器，不能外推到所有手機 Web。

保留三個時間，而非只報最快的一個：

| 指標 | 起點 → 終點 | 意義 |
|---|---|---|
| core | `beamSolve` 進入 → 回傳 | 搜尋與核心收尾 |
| delivered | 按下求解、輸入已備妥 → 呼叫端取得結果 | 包含搜尋前排程，不包含最後 React 提交 |
| ready | 同一請求起點 → 結果的 `useLayoutEffect` | 結果 DOM 已提交，可供畫面使用；不是實體螢幕顯示完成證明 |

DOM 上的 `data-solver-runtime-ms`、`data-solver-delivered-ms`、`data-solver-ready-ms` 可直接採集。每次保留原始值，報 p50、p95、p99、最大值、超過 160ms 的比例；缺值視為未驗證，不能當作 0ms。另報「準時回應率」「準時有合法候選率」「準時全需求成功率」，`no_candidate` 只屬於第一種。

使用 `performance.now()` 的單調時鐘。若未來改用 Worker，跨執行環境的時間必須透過各自的 `timeOrigin` 對齊。[MDN 計時文件](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/High_precision_timing)

## 必須先過的正確性門檻

用 `tools/solver_reference.mjs` 從原盤面逐步交換、重播路徑並重新消除，不能相信 solver 自報的 combo／success。它不呼叫正式求解器的消除函式。

| 面向 | 必驗案例 |
|---|---|
| row0 | 起手注入；普通起手碰 row0 結束；row0 保持原值；只複製種類、不複製標記；row0 起手後不得再進 row0 |
| 路徑 | 四向／八向；固定 START/END；X1 不可碰；X2 只能終點；重訪；最大步數；非法座標；空結果 |
| 消除 | 六種類各自 1～5 最低門檻；直橫／四向相連；長線不拆組；相接的已消線合組；無隨機補珠 |
| 狀態 | N1 永不消；N2 首批不消、有真正首消後才能疊消；標記隨一般交換移動 |
| 需求 | 依清單優先順序；指定尺寸與組數；同批可滿足多需求；部分完成不冒充成功 |
| 盾 | 首消粒數；指定種類 combo 相等；九種 3～5 矩形；五顆十字/L/T 與旋轉；指定種類／任意；附加第六顆的反例 |
| Top10 | `7+1` 與 `6+2` 分開；同簽章不重複；排序一致；高層需求相同時最短步數；不存在的組不湊數 |

線上結果排序為 `[合法性, 各符石需求完成旗標…, 解盾完成順位, 首消目標完成, 總combo, -步數]`，逐欄比較，不使用加權總分。需求順序改變時，偏好的未完全成功解也可能改變。未達成需求的距離僅用於同等結果的搜尋引導。

沿用現有專案語意：START/END 約束原始座標；疊消只有現存珠重力掉落，不補隨機珠；相等盾要求選定種類皆有消除再比較；矩形與五顆形狀使用完整消除組判定。

## 新舊版的配對品質比較

同一原始盤面、設定、seed、160ms 預算形成一組比較，交錯 A→B 與 B→A。兩邊都真正執行暖機，暖機不算樣本。不同重複次數是同一盤面的重複測量，不能假裝增加獨立樣本數。

1. **首要結果**：每組依獨立驗證後的需求向量判新版勝／負／平；再列每個需求、盾、首消目標的成功率差，單位用百分點。
2. **Combo**：僅在所有更高優先條件相同時比較總 combo，另列首消與疊消，不用平均總 combo 掩蓋需求退步。
3. **步數**：僅比較相同 `首消+疊消` 簽章、相同更高層結果的代表。`舊步數-新步數` 為節省步數；除以舊步數才是相對節省率。舊版 8 combo/20 步變成新版 6 combo/10 步不是步數優化成功。
4. **Top10**：合法組數、重複率、原生順序違規數、各組最短步数、全需求成功組數、共同簽章覆蓋率。缺組與缺解保留在分母。
5. **穩定性**：每盤重複成功率、結果簽章變化率、步數離散程度、最差一次；best-of-R 只做診斷，不代表單次使用體驗。
6. **延遲**：新舊 p95 改善率為 `(舊p95-新p95)/舊p95`；務必同時給絕對毫秒及品質變化。

用原始盤面作群集 bootstrap，重抽盤面時連同其所有情境與重複次數一起抽取，計算差值的 95% 信賴區間。不能把同盤的重複執行當成彼此獨立；沒有足夠獨立盤面時，只報描述統計，不宣称顯著改善。

正式升版門檻：非法路徑、錯報成功、重複分組、錯誤消除必須為零；高層需求的退步不能被低層 combo 或速度抵銷。發現配對退步就列出反例，標記需評估的取捨；任何平均數都不能直接產生「全面進步」結論。`tools/perf_eval.py` 已加入保守的反假優化門檻，但其通用協定檢查本身不等於獨立遊戲規則驗證。

## 最佳解與最短步數如何量化

- **庫存上界**：`src/solver/comboBound.js` 計算每色 `floor(可用珠數/minClear)`，row0 最多一次替換種類，總珠數不增加。首消排除 N1/N2，總消只排除 N1。這放寬了形狀、可達路徑及解盾等限制，不能稱為可達的最大 combo。
- **小範圍精確答案**：`tools/solver_oracle.mjs` 完整枚舉明確的起點與步數範圍；只有 `exhaustive=true` 時，才可以說已證明該範圍最大 combo 及其最短步數。中途碰到時間／狀態數上限，一律 `optimalityProven=false`。
- **已證明最優差距**：同一規則與範圍，報 `oracle最佳combo-線上combo`；只有更高層條件與 combo 相等時，才報 `線上步數-oracle最短步數`。另報精確 Top10 的簽章找回率。
- **大型盤面**：離線長時間多次搜尋產生 best-known 參考庫，保留來源及時間。線上解到 best-known 的差距只是已知差距，不是全域最優證明；若在線上調參看過測試盤，該盤應移到開發集合。
- **收斂曲線**：固定 20/40/80/120/160ms 節點，保存當下最佳需求向量、combo、步數及合法組數。用同一時間點配對，才知道進步來自更早找到合格解、更多 combo，或最後的縮路。

## 全面驗收矩陣與重跑

目前提供手算規則測試、獨立重播、六種代表情境的核心 A/B、受限範圍 oracle 比對及實際 Web 計時。這些已實作的測量不等於所有裝置與所有設定都已大規模跑過。

下一輪正式驗收應覆蓋 `tools/perf_eval_scenarios.json` 的 73 類，以及零／一／二／三個盾、各符石種類、所有矩形尺寸、兩種消除模式×五門檻、四向／八向、疊消开关、row0开关、標記組合、短／長步數、可解／已證明無解／未知。用平衡單項案例，加上 pairwise 組合及有意設計的高難衝突案例；隨機盤面不能替代稀有規則測試。

核心 A/B 會排除既有 `fixed_test_suite.json` 的 4000 盤與 proxy corpus 的 100 列，保存去重與hash資訊。本次凍結測試結果若被拿來調參，下次應換全新 seed／盤面。

```powershell
node --test tools/test_solution_ranking.mjs tools/test_solver_reference.mjs tools/test_solver_oracle.mjs tools/test_combo_bound.mjs tools/test_web_solver.mjs
python -B -m unittest discover -s tools -p test_perf_eval.py -v
node tools/compare_web_solver_update.mjs --boards 5 --repeats 3 --out reports/solver-update-20260909/core-ab.json
node tools/compare_solver_oracle.mjs
npm run build
npm run preview -- --host 127.0.0.1
```

核心 A/B 對前版加上協作式截止與端點觀察，讓前版也能參與相同 160ms 的搜尋品質比較。這會增加兩邊觀察成本，前版可能到下一個端點才停，也可能尚未刷新原生候選池；因此它不是前版原始 UI 延遲，也不能用前版此處的截止超時率宣称新版瀏覽器延遲改善同樣比例。實際瀏覽器延遲必須另外測量。

此次未驗證：所有手機瀏覽器、背景分頁、CPU 壓力及長時間熱降頻、每種多盾組合的成功率、全域最大 combo、任意盤面的全域最短路徑、實際螢幕呈現延遲。一般 Web 的協作式截止也不能保證作業系統排程與 GC 永遠不延遲；應用實測的分位數與超時率驗收，而非將 160ms 設定值當作保證。
